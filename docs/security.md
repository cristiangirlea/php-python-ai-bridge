# Security boundaries

This service is designed for trusted application-to-service traffic on a private network. Do not expose the example routes or Python server directly to the internet. Across hosts, put a TLS proxy in front of the worker as [Cross-host use behind TLS](integration.md#cross-host-use-behind-tls) shows.

The standard-library `http.server` worker is supported only behind a reverse proxy that terminates TLS, normalises HTTP and enforces its own limits (the TLS example's Caddy or an operator's equivalent), or bound to loopback or a private interface for a co-located client. The default `--host` is `127.0.0.1`. A non-loopback bind warns at start unless `BRIDGE_TRUST_NETWORK=1` acknowledges this deployment rule; that setting suppresses the warning, it does not enforce the boundary. See [operations](operations.md#1-deployment-topologies) for the warning and proxy limits.

The TLS example refuses declared lengths above 262144 bytes before dialing the worker over HTTP/1.1 and HTTP/2, including leading-zero spellings, with the worker's fixed 413 JSON. Exactly 262144 bytes can be forwarded, and Caddy refuses non-numeric lengths with 400 over HTTP/1.1. Over HTTP/2, a non-numeric length reaches worker authentication (401 without a token). Its streaming body limit also applies without a declared length, but does not guarantee rejection before contacting the worker: chunked uploads over HTTP/1.1 remain chunked upstream and the worker refuses them with 400 before authentication; an oversized chunked upload may receive proxy 413 after reaching the worker. Buffering makes bounded bodies available before dialing to reduce races with early worker refusals; it does not guarantee isolation for unknown lengths.

- Generate a service token of at least 32 non-whitespace ASCII characters. Never commit it. A token reaches only the jobs it submitted: another token's job answers 404 as if it did not exist, and idempotency keys are per token. Give each application, and the MCP server, its own token in `BRIDGE_TOKENS` or `BRIDGE_TOKENS_FILE` (mode 0600 or stricter), so one can be revoked by removing its entry and restarting the worker without touching the others, and a leaked token exposes only its own client's jobs. Capacity is shared, so by default any token can fill the worker and starve the others; set `BRIDGE_OWNER_CAPACITY` to cap one token's queued, running and retained jobs, which is off by default. A token at its cap gets the same 429 as a full worker, so it learns nothing of the other tokens' load; the cap is the same for every token, so where it times the number of tokens exceeds the capacity the tokens together can still fill the worker: size it against both shared limits and the number of tokens; `/healthz`, `/readyz` and `/metrics` answer every token, and the metrics carry the token names, never the tokens. The job table stores a job's owner by name only.
- Enforce end-user authentication and per-job ownership in the PHP application. The example deliberately omits those application-specific policies and publishes no ports.
- Only trusted task implementations are allowed. The service removes `BRIDGE_TOKEN` and `BRIDGE_TOKENS` from its environment before it starts its child processes, and reads `BRIDGE_TOKENS_FILE` without putting its content there, so no token is in either their environment nor their initial environment block (`/proc/<pid>/environ`), which a removal inside the child would leave as it was; the children never speak HTTP. Everything else in the service environment stays visible to them, except that the service sets `ORT_DISABLE_TELEMETRY=1` before it starts each child, overriding any inherited value, so that ONNX Runtime's telemetry uploader (on from import since 1.31) never starts; the only outbound connection a child could open is thus closed before the runtime loads. A child serves many jobs in turn and keeps its loaded models; it keeps no reference to a finished job's input or result, but the memory they used is freed, not wiped, so a core dump of a long-lived child can still hold earlier jobs' data where a process that died after each job could not. They are not suitable for arbitrary user-provided scripts.
- Container configuration uses a non-root user, read-only filesystem, dropped capabilities, no-new-privileges, CPU/memory/PID bounds, and an internal-only network for execution. It mounts only this checkout and the optional dependency/model cache, never a Docker socket or home directory.
- Dependency acquisition is separate and internet-enabled. Execution installs hash-checked wheels from the local cache without internet access. The model downloader retrieves fixed files at a pinned revision and checks their hashes; it does not execute model-repository code.
- CI runs on GitHub's hosted runners only, because the repository is public. GitHub runs a pull request's workflows as the pull request has them, so a fork's pull request executes its own code, workflow edits included; on a disposable runner of GitHub's that holds nothing of the maintainer's, that is the intended boundary. No workflow names a self-hosted runner, and `tests/python/test_workflows.py` fails if one does again; a fork can edit that test along with the workflows, so while any self-hosted runner is still registered for the repository, keep requiring approval for outside contributors' workflow runs, and unregister it so that there is none a pull request could route its code onto. Every action a workflow uses is pinned by commit hash, and the `actions/checkout` step does not persist credentials; the same test fails if either changes.
- Model files, native libraries and runtime dependencies still carry supply-chain risk. Review upgrades, regenerate locks deliberately and rerun tests before changing pins. Weekly, Dependabot proposes updates to the actions, wheels and Composer packages (for the wheels, a bump to the `requirements-*.txt` manifests: Dependabot does not read the hash locks, which are regenerated by hand from the new pins and checked with `pip download --require-hashes` before they land), the `audit` job in `model-smoke.yml` checks `requirements-model.lock` and `requirements-mcp.lock` with `pip-audit` and `composer.lock` with `composer audit` (accepted advisories, each with its reason, are in `.github/audit-ignore.txt`), and CodeQL scans the Python code and the GitHub Actions workflows ([SECURITY.md](../SECURITY.md) lists every scan, OpenSSF Scorecard among them); GitHub's CodeQL does not support PHP, so the PHP client is covered by PHPStan at level max and the hostile-peer tests instead; report a vulnerability privately as [SECURITY.md](../SECURITY.md) says.
- `BRIDGE_CAPACITY` bounds active jobs and `BRIDGE_RESULT_CAPACITY` bounds retained results at admission. Jobs already accepted can finish after the result store fills, so retained results can exceed the result capacity by at most the active capacity; the sum bounds the job table. In a lexical-worker container, the parent process's `/proc/self/status` RSS grew from 27,744 to 36,576 KiB after retaining 1,024 successful rerank results of 32 short documents each, about 8.4 MiB per 1,000 results. For 1,024 embed results of 32 texts and 384 dimensions, parent RSS grew from 27,916 to 635,596 KiB (about 593.4 MiB). At the default 384 + 128 limits, that workload extrapolates to about 324 MiB parent RSS; children, persistence and other memory add to this against compose's 512 MiB limit. Raising `BRIDGE_RESULT_CAPACITY` needs a matching container memory budget; shortening `BRIDGE_RETENTION_SECONDS` instead admits more work with the same result count if clients collect promptly ([sizing](operations.md#2-sizing)). Size and monitor both limits for actual inputs and results; these measurements are not bounds.
- Requests and results may contain sensitive documents. They live in RAM, may be present in process/core dumps, and are not encrypted by this service. With `BRIDGE_STATE_DIR` set, `jobs.sqlite` (and its `-wal` and `-shm` files) in that directory holds each retained job's ID, task, status, error, progress, deadline, idempotency key, submission and finish times, and its result until retention expires; it never holds a job's input, though results such as redacted text, rankings and embedding vectors reveal much of it. SQLite's `secure_delete` overwrites an expired row in the database file, but older copies of its page can stay in the `-wal` file until a checkpoint reuses it, so keep the directory on tmpfs or an encrypted volume readable only by the service user (compose's `worker` uses a 64 MB tmpfs owned by uid 65532 with mode 0700). Minimize retention and use appropriate host/storage policies. Embedding vectors are derived from their input text and can reveal much of it; store and transmit them with the same care as the text.
- Redaction is assistive, not a compliance control. The rules find only the structured identifiers they recognise, and the optional named-entity models were trained on English news, so their recall on names from other domains or languages is lower and unmeasured here; review redacted output before treating it as free of personal data. The model files are third-party ONNX conversions of the original weights, pinned by revision and hash but not signed by the original author.
- The MCP server is a client of this service for an AI agent over stdio, where there is no authentication: the host that launches it inherits its trust, and it holds the token from its environment and never returns it. Running it over HTTP or SSE would be a new authorisation surface that the bearer token does not cover; it is out of scope. An agent can be prompt-injected and can then fill a worker's capacity, so point the MCP server at a dedicated worker, never at one serving a production application; compose's `mcp` and `mcp-model` each have their own. It reads files only under `BRIDGE_MCP_ROOT` and writes none; snippets it returns are the agent's own file content and enter the agent's context like any file it reads. Index files built for `bridge_search` are derived data: `index.json` holds every chunk's text verbatim and `vectors.f32` holds vectors that can reveal it, so keep them with the same care as their sources. The builder runs with the service token like the PHP client and is the only component that writes, into the directory the operator names.
- `GET /metrics` reveals aggregate numbers only: how many jobs of each task were submitted, refused for capacity and ended in each terminal status, how many are queued and running, the pool's size and readiness, the concurrency and capacity settings, the backend name, and histograms of job and queue durations per task. It never reveals a job ID, idempotency key, input, result, error message, model path or the token; its label values come from fixed sets, never from a request. Counts and timings still describe the traffic (how busy the service is, which tasks run, how long they take), so the endpoint is behind the same service token as every route: scrape it from inside the private network with that token, never through a public route. How often it is scraped is the operator's concern; a scrape copies a few counters under the store's lock and formats them outside it.
- The worker writes no request/job/lifecycle log unless `BRIDGE_LOG=json` is set; a non-loopback startup warning still goes to stderr unless `BRIDGE_TRUST_NETWORK=1`. With JSON logging enabled, it writes lines on stderr for each request (method, route template, status, duration, the token's name), each job that ends (job ID, task, the token's name, terminal status, queue and run times) and the start, drain and stop (the backend, the numeric limits and how many tokens are configured, how many jobs a drain or stop cut short). It never writes an input, result, header, path or query string, idempotency key, token, error message or exception text: the formatter keeps only its fixed keys and checks each value against a fixed set, a number, a job ID in either form or the token-name pattern, writing `null` otherwise. Job IDs and token names still link requests to clients, and timings still describe the traffic, so keep the log with the same care as the metrics. Internal exceptions become generic task errors. This is not a full observability or compliance solution; [the protocol](protocol.md#logging) has the schema.
- Cancel/timeout terminates the task process, but cannot roll back previously completed external effects. No task in the prototype modifies an external system.
- `/healthz` proves HTTP service availability, not model integrity, ability to spawn processes or successful inference. `/readyz` adds that a child process started and loaded the configured backend's models without an error; it does not prove that they infer correctly. An ONNX worker checks before it starts that each model directory holds its tokenizer and model files and refuses to start otherwise; that proves presence, not integrity, which the fetcher's hashes establish. Use a controlled model smoke test for inference validation.
- A drain (the first SIGTERM or SIGINT) keeps the inputs of running jobs in their children until they finish, the deadline passes or a second signal ends it, and keeps every finished result until the process exits. It drops the input of every job still queued at once: the job is failed as `service_restarted` and nothing of it is replayed, so a caller resubmits. Results and inputs are never written anywhere for a later process; with `BRIDGE_STATE_DIR` the job table holds what it always holds (never an input). The process ends with its memory, so after it nothing of a job survives outside that table.
- The worker answers a full connection budget (32 connections) with a fixed 503 written as it accepts, without reading the request or checking its token, and refuses a request line over 8 KiB or a header block over 16 KiB with 431 before reading the rest; neither answer says anything about a job or a setting. These bound what one client holding connections or sending a large head can make the worker read or keep; they are not rate limiting, which belongs in front of the worker.

The FrankenPHP executable is copied from its pinned image into a task-only executable tmpfs. This removes upstream file capabilities without granting the container capabilities. Other temporary storage is non-executable; the optional Python dependency tmpfs must permit native library mappings.
